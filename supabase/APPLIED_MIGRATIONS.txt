# supabase/APPLIED_MIGRATIONS.txt
#
# Operator-maintained manifest of every Supabase migration that has been
# applied to the live production database. The companion test
# (tests/migrationReadiness.test.ts) fails CI if a new .sql file lands in
# supabase/migrations/ without being appended here, or if this file lists a
# migration that no longer exists in the directory.
#
# Workflow:
#   1. Author a new supabase/migrations/YYYYMMDD_*.sql
#   2. Apply it to the live Supabase instance (SQL editor or pg.Pool runner)
#   3. Append the exact filename (one per line) to THIS file in the same commit
#   4. The CI vitest job will then go green on the next push
#
# If you need to roll back a migration:
#   - Write a NEW compensating migration (never edit applied SQL)
#   - Apply the compensating migration
#   - Append the new compensating migration to this file
#   - Leave the original line in place so the directory state stays consistent
#
# Format:
#   - One filename per line, exactly matching the .sql basename
#   - Lines starting with `#` are comments (ignored by the test)
#   - Blank lines are ignored
#   - Order does not matter (the test compares as sets, not arrays)
#   - The test does NOT verify the migration was actually applied to prod --
#     that's a manual contract. This file is the source of truth for "what
#     do we EXPECT to have been applied" so CI can flag drift between the
#     on-disk migrations/ directory and the expected applied state.
#
