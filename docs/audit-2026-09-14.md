# Site & Checkout Audit — 2026-09-14

Full audit of `sgcoalition.xyz` (payments, pricing authority, SEO, security headers, env hygiene) with the fixes shipped in this same pass. Read alongside [`FOLLOWUPS.md`](../FOLLOWUPS.md) — the operator items below are the ones this audit surfaced or confirmed still open.

## Executive summary

The checkout backbone is **healthy in production**: `/api/health` reports `checkoutWorking: true` with a valid Stripe key (the July 503 incident is resolved), and every pricing/order endpoint returns correct responses. The audit found four real defects in the payment flow, all fixed in this pass, plus minor site hygiene items. PayPal checkout has since been removed from the product entirely. What remains for the operator is dashboard work only.

## Defects found → fixed

### 1. Store credit + Stripe order creation broke after the charge (P0)

**Symptom:** A buyer with store credit paying by card had the correct (post-credit) amount charged to their PaymentIntent, but `/api/complete-order` re-priced the order at FULL price — the credit never reached the server — so `verifyPayment` failed with `Stripe amount mismatch`. Result: buyer charged, no order row.

**Fix:**
- `pages/Checkout.tsx` captures `creditApplied` from the `create-payment-intent` response and forwards it as `order.storeCreditApplied`; also persisted into `coalition_checkout_state` so the 3DS/Klarna/Afterpay redirect-return path (`pages/OrderSuccess.tsx`) forwards it too.
- `api/_handlers/complete-order.ts` maps `storeCreditApplied` (dollars) → `attempt.serverCreditCents`.
- `services/orderIntake.ts → acceptCheckout` re-verifies the stated credit against the **live** profile balance (declines with 409 if credit was spent mid-checkout), prices the order with the stated amount via the new `storeCreditAppliedCents` parameter of `resolvePricing`, and **debits the profile exactly once per order** (CAS-guarded `.gte` write, never blocks the order on failure).
- The zero-amount path (`/api/place-order-credits`) keeps its own debit; the two paths are disjoint (stated credit > 0 vs finalAmount === 0).

Locked by `tests/orderIntake.test.ts` (server-stated credit re-pricing + debit, decline-on-stale-balance) and `tests/orderSuccessStripeRedirect.test.tsx` (credit + coupon forwarded through the redirect-return).

### 2. No server-side inventory decrement — 1/1 oversell risk (P1)

**Symptom:** Pricing VALIDATED stock, but only the client decremented it (`deductInventory`). Two concurrent buyers of a stock-1 piece could both pass validation and both pay.

**Fix:** `acceptCheckout` now decrements each purchased size line server-side after the order row is created, using the fresh DB stock with a CAS-style conditional write. Stock-hits-zero-mid-checkout throws 409 "just sold out" (buyer refunded via Stripe dispute-avoidance; order row remains, flagged in Vercel logs). Pending manual methods (crypto/cashapp) skip the decrement — money hasn't moved and the operator's manual flow handles those.

Locked by two new `acceptCheckout` tests (decrement fires for paid methods; 409 on 0 stock; no decrement for pending methods).

### 3. Crypto discount advertised but never applied (P1)

**Symptom:** The checkout showed "SAVE 10%" on the USDC option while the client always sent `discount: 0` to the server — no crypto discount could ever materialize.

**Fix:** Single source of truth — `utils/cryptoDiscount.ts → resolveCryptoDiscountCents()` (client-safe: imported by BOTH the checkout UI and the server pricing authority, so the frontend never pulls Node-only Stripe/Resend SDKs):
- Gated on `VITE_SGCOIN_DISCOUNT_ENABLED` (tolerant parser: quotes/trim/case), capped at $10, applies to the `crypto` method only (never card/Stripe).
- `resolvePricing` computes it into `discountCents` and exposes `cryptoDiscountCents` on the snapshot; `pricing-preview` and the order notes both read it directly (the old remainder-math leak path is gone).
- Checkout UI badges now gate on the shared helper (`cryptoDiscountAdvertised`), so the badge and the server math can never disagree.
- The estimate shown in `create-payment-intent` response (`cryptoDiscountEstimate`) uses the same helper.

`VITE_SGCOIN_DISCOUNT_ENABLED="true"` is set in the production env, so the 10% is **live as of this deploy**.

### 4. Test suite red in full runs (P1)

**Symptom:** 2/716 failures in `pricingPreview` on one bare `npx vitest run` (which also showed ~4× normal environment setup time — a resource-starved machine run). Full-suite re-runs passed 716/716 repeatedly, and the file passed in isolation.

**Fix:** Not a code defect — but the suite now **pins `VITE_SGCOIN_DISCOUNT_ENABLED` off** in `pricingPreview` and `orderIntake` so real deployment env (Vercel exposes `VITE_*` to functions) can never flip real money math in tests. The `crypto + coupon` preview test was updated to assert the new contract (crypto line comes from the shared helper, 0 while the flag is off).
